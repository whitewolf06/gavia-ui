## 0а. Токены и темы (дополнение 15 ноября)

Поводом стал PR #8 версии 1.1.0: 4064 добавленные строки при небольшой правке кода.

### Как устроено сейчас

- Источник один: `packages/ui-kit/tokens/source.json`. У токена есть значение по умолчанию (`value`) и, при необходимости, отличия для отдельных тем (`themes`).
- `pnpm tokens:sync` выписывает **полный набор** токенов в `styles/base.css` (`:root`) и в каждую из пяти тем под `[data-wl-theme="…"]`, а также в `src/design-system/tokens.generated.ts` и `tokens/catalog.generated.json`.
- Канонических токенов в `source.json` было 447 в 1.0.0, стало 533 в 1.1.0. Добавлено 86: 11 foundation, 18 semantic и 57 component. Число 538 получается при подсчёте объявлений в файле темы: пять из них повторяются в блоке reduced motion. Руками правятся только `source.json` и стили компонента.

**Почему полный набор в каждой теме — не ошибка.** Ссылка `var()` внутри токена вычисляется там, где токен объявлен, а дальше наследуется готовое значение. Если компонентный токен объявить только в `:root`, секция с локальным `data-wl-theme` получит его посчитанным по теме страницы. Локальная тема на секции заявлена в `docs/guide/theming.md`, и работает она именно потому, что каждая тема самодостаточна.

### Оценка подхода

Подход современный и распространённый. Устаревшим или неэффективным для потребителя его назвать нельзя.

| Подход | Кто так делает | Статус |
|---|---|---|
| Sass-переменные, темы на этапе сборки | Bootstrap 4, старые Element и Vuetify | уходит |
| Стили и токены считаются в рантайме через JS | Ant Design 5, Naive UI | от него отходят: Ant Design 6 перешёл на CSS-переменные |
| CSS-переменные, которые библиотека вставляет на страницу через JS | PrimeVue 4 | актуален, но требует рантайма |
| **Статические CSS-переменные, тема по атрибуту** | Bootstrap 5.3, Radix Themes, shadcn/ui, Nuxt UI, Gavia UI | основное направление |

Сравнение сделано по знанию устройства этих библиотек; поиском подтверждены только общие факты про PrimeVue, Nuxt UI и Ant Design 6.

**Что хорошо для потребителя:**
- Нет рантайма и плагинов сборки: два CSS-файла и атрибут. С SSR нет мигания темы.
- Переопределение обычным CSS на любом уровне; слои гарантируют приоритет стилей приложения.
- Локальная тема на секции.
- Малый вес: тема — 4,4 КБ gzip, `base.css` — 4,9 КБ gzip.
- Контраст проверяется при сборке, каталог токенов типизирован.

**Где Gavia UI уступает лучшим:**
1. **Полнота.** В PrimeVue и Material каждый компонент настраивается токенами целиком. Здесь часть размеров зашита в стили (задача B6).
2. **Своя тема из одного цвета.** В PrimeVue есть `definePreset`, в Nuxt UI основной цвет задаётся строкой конфига. Здесь есть конструктор тем на сайте, но в коде приложения токены переопределяются вручную (T1–T4, раздел 0б).
3. **Связка с Tailwind.** Проекты на Vue и Nuxt часто ждут, что токены кита доступны как тема Tailwind (задача E11).

### Цена текущей схемы

Замер на 1.1.0 против 1.0.0:

| Файл | 1.0.0 | 1.1.0 |
|---|---|---|
| `themes/gavia.css` | 20,6 КБ, 3,8 КБ gzip | 26,1 КБ, 4,4 КБ gzip |
| `styles/base.css` | 23,3 КБ, 4,2 КБ gzip | 28,9 КБ, 4,9 КБ gzip |

- 86 новых токенов записаны одинаковыми строками в `base.css` и во все пять тем: сравнение добавленных строк не показало ни одного отличия.
- Цена для потребителя — около 0,65 КБ gzip на файл за 86 токенов. Сейчас это мелочь.
- Каждый новый токен стоит примерно 30 строк диффа: запись в источнике, шесть строк CSS и две сгенерированные копии. B6.0 убирает только шесть объявлений CSS на такой токен; источник и каталоги остаются. Это не сокращение всего токенного диффа.

### Вывод

- Базовые и семантические токены оставить как есть: полный набор на тему — оправданная цена за локальные темы.
- Объём новых токенов зависит от выбранных сценариев B6. Текущая добавочная цена невелика; сама по себе она не требует смены схемы генерации.
- Для одного **нового компонентного** токена можно проверить значение по умолчанию в самом компоненте — необязательный эксперимент B6.0, не предпосылку всего B6:

```css
/* core.css — токен нигде не объявлен, компонент берёт запасное значение */
.wl-btn { font-weight: var(--wl-btn-font-weight, 500); }

/* если значение по умолчанию идёт из темы — запасным ставится семантический токен */
.wl-btn { border-radius: var(--wl-btn-radius, var(--wl-corner-button)); }
```

  Запасное значение вычисляется на самом компоненте. Но незаданный токен наследует пользовательское переопределение родителя сквозь вложенную другую тему; нынешнее объявление в каждой теме восстанавливает на её границе собственное значение по умолчанию. Потребитель по-прежнему может задать `:root { --wl-btn-font-weight: 600; }`, однако распространение этого значения становится частью нового публичного контракта.

- **Контракт эксперимента:** прежде чем выбирать схему по одинаковому значению во всех темах, определить поведение inherit/reset на границе вложенной темы. Отдельно проверить aliases, объявляемые на контейнерах `wl-type-scale` и `wl-fluid`: унаследованное уже вычисленное значение не обязано пересчитаться в дочерней теме. Токены с отличиями между темами остаются в нынешней полной схеме; объявление только в одной теме не обеспечивает сброс в другой.
- **Цена:** генератор должен научиться описывать токен в каталоге без записи в CSS; значение по умолчанию не видно в DevTools как объявленная переменная; появляются два вида токенов и дополнительные проверки соответствия CSS каталогу. Принятое правило потребуется записать в `AGENTS.md`. Экономия касается CSS, а не записей в источнике и сгенерированных каталогах.
- Существующие токены не трогать: они публичные, и текущая схема для них работает.

## 0б. Свои темы и кастомизация (дополнение 15 ноября)

Вопрос: насколько удобно потребителю сделать тему под свой проект и нужен ли для этого конфиг с генератором в npm-пакете.

### Что уже есть

- **Переопределение токенов** обычным CSS на любом уровне.
- **Пример `examples/custom-theme`:** слой бренда поверх готовой темы — селектор `[data-wl-theme="gavia"][data-wl-brand="my-brand"]` и три переопределённые роли, шесть строк CSS.
- **Конструктор тем на сайте:** выбор базовой темы, имя, восемь цветов, живой предпросмотр, проверка контраста. Остальные цвета (hover, мягкие состояния, границы) выводятся автоматически. Экспорт: готовый CSS, JSON и задание для агента.
- **Расчёт отличий уже реализован:** `createThemeOverrides` в `apps/playground/src/theme-builder/palette.ts` возвращает изменения относительно базовой темы. T2 — выделение этой логики из UI/i18n и оформление публичного API, а не новый генератор с нуля.
- **Версия JSON-схемы уже есть:** `schemaVersion: 1`. Parser намеренно игнорирует экспортные `overrides` и `semanticBindings`; перед CLI нужно разделить пользовательские настройки и производные данные и определить совместимость формата.
- **Переключение тем:** `useWlTheme`, `resolveWlTheme`, `wlThemeInitScript` (светлая, тёмная, системная, без мигания при загрузке).
- **Другие уровни настройки:** `pt` на всё приложение или на экземпляр, слоты, стабильные классы и слои CSS, реестр иконок, локаль, классы `wl-fluid` и `wl-type-scale`.

Набор возможностей богатый. Слабое место — путь к ним.

Проверка контраста в конструкторе покрывает отдельные пары цветов и их пороги. Она не обещает полной доступности темы или всех состояний компонентов; это ограничение должно сохраниться и в публичной функции, и в CLI.

### Чего не хватает

1. **Нет гайда «как сделать свою тему».** `docs/guide/theming.md` описывает палитру Gavia (цвета, контраст, радиусы), а не порядок действий. `tokens.md` — 20 строк без примера. Путь разбросан по трём документам и README примера.
2. **Пример неполный.** Он меняет `--wl-accent`, `--wl-text-accent` и `--wl-focus-color`. Основная кнопка берёт цвет из отдельных `--wl-palette-action-primary-*` (фон, hover, active, текст) и остаётся цвета Gavia. Полный ребрендинг затрагивает не меньше 11 из 42 токенов палитры, и их список нигде не приведён. README примера сам предупреждает, что роли hover и active нужно задать отдельно.
3. **Логика генерации темы живёт только в Playground** (`apps/playground/src/theme-builder/palette.ts`). В npm-пакете нет ни функции, ни команды. JSON из конструктора, по словам самого гайда, библиотекой не загружается.
4. **CSS из конструктора — полный снимок на момент экспорта.** Новые токены отсутствуют в старом файле, но остаются в актуальном `base.css`. Если своя тема применяется на `html/:root`, новые aliases могут корректно вычислиться через её палитру; обязательный повторный экспорт после каждого минора из этого не следует. Для вложенной темы с новым именем есть риск унаследовать aliases, уже вычисленные по палитре родителя. Надёжный вариант для текущей модели отличий — базовая тема и слой бренда на одном элементе. Иные схемы возможны, но требуют собственного контракта объявления aliases и проверки наследования.

### Рекомендация

Цель: у потребителя есть понятный путь настройки в коде и, после выпуска инструментов, через функцию и команду. В пересобранном плане T1 находится в шаге 2; T4, T2 и T3 — в шаге 3.

- **Основным документированным путём сделать слой бренда поверх готовой темы на том же элементе.** Для этого нужны гайд и полный пример с ролями primary/hover/active, ссылок, фокуса и выбранных состояний (T1). Будущие функцию и CLI не описывать как уже поставленные возможности.
- **Выделить существующую генерацию из Playground в публичную чистую функцию** (условно `createWlThemeCss({ base, name, palette })`) после согласования API и контракта полного экспорта или отличий. Она возвращает CSS и отчёт по проверяемым парам контраста; конструктор использует ту же логику (T2).
- **Команда генерации с конфигом в проекте потребителя** (T3) — тонкая обёртка над той же функцией. Сначала T2 и разделение пользовательских настроек и производных полей уже существующей JSON-схемы, затем CLI. Решение включить команду в план принято владельцем 15 ноября.
- **Конструктор должен уметь применить черновик ко всему Playground** с кнопкой отмены (T4). Сейчас предпросмотр намеренно изолирован: по `docs/guide/theme-builder.md`, правка палитры не меняет шапку и другие страницы. Для глобального применения достаточно текущего `createThemeOverrides`; публичный T2 не является зависимостью. Нужно согласовать переключатель темы, переходы, восстановление до первого кадра и удаление временных переопределений при отмене.

## 3. Найденные дефекты

### D1. Локаль и реестр иконок застывают на Vue 3.4   · P0

**Где:** `packages/ui-kit/src/config.ts`, функции `useWlLocale` и `useWlIcons`.

**Суть.** `computed` создаётся внутри `setup` первого компонента, который запросил локаль, и кэшируется в модульном `WeakMap`. Во Vue 3.4 такой `computed` привязан к области эффектов этого компонента. Когда компонент размонтируется, `computed` останавливается и навсегда возвращает последнее значение. После этого `useWlConfig().setLocale()` не обновляет тексты ни в существующих, ни в новых компонентах приложения.

Типичный сценарий: первым локаль прочитал `WlSelect` на странице маршрута, пользователь ушёл со страницы и переключил язык.

**Проверка.** Паттерн из `config.ts` воспроизведён отдельным скриптом (компонент A и компонент B делят кэшированный `computed`, A размонтируется, локаль меняется):

| Vue | Текст компонента B после смены локали |
|---|---|
| 3.4.38 | остался `en` — дефект |
| 3.5.22 | стал `ru` — работает |

Vue `^3.4.0` — заявленный минимальный peer, а `devDependencies` пакета закреплены на 3.4.38. В `tests/config-reactivity.test.ts` сценария с размонтированием первого потребителя нет.

**Сверка Codex 15 ноября.** Дефект подтверждён на реальном `config.ts`, скомпилированном только в памяти, и Vue custom renderer. На Vue 3.4.38 после размонтирования первого потребителя A и вызовов `setLocale` / `setIcons` второй B сохраняет `Initial` / `IconOne`, а вновь созданный C получает старую локаль. На Vue 3.5.40 B получает `Changed` / `IconTwo`, C — новую локаль. Проверены локаль и реестр иконок; код библиотеки в файлах не менялся.

**Исправление.** Создавать общий `computed` в отсоединённой области: `effectScope(true).run(() => computed(...))`. То же для `iconRegistries`. Эта замена проверена только в памяти на Vue 3.4.38: B получает `Changed` / `IconTwo`. При реализации сохранить владение конфигурацией на уровне приложения; регрессия должна проверять размонтирование A, обновление локали и иконок, живого B и нового C.

### D2. ID заголовков Dialog и Drawer совпадают с `useId()` Vue 3.5   · P0

**Где:** `utils/useWlId.ts`, `WlDialog.vue:95`, `WlDrawer.vue:99`.

**Суть.** `useWlId()` по умолчанию возвращает `v-0`, `v-1`… Штатный `useId()` Vue 3.5 выдаёт идентификаторы того же вида (проверено: `v-0`). Большинство компонентов добавляют свой префикс (`wl-select-list-…`, `wl-field-…`), но заголовки `WlDialog` и `WlDrawer` используют значение как есть. Если приложение на Vue 3.5 само вызывает `useId()`, в документе появляются два элемента с одинаковым `id`, и `aria-labelledby` диалога может указать на чужой элемент.

**Статус проверки.** Первоначальный вывод был сделан по коду и формату `useId()`; тот же код присутствует в опубликованном `dist` 1.0.0. При сверке Codex 15 ноября дефект подтверждён на реальных `WlDialog.vue` и `WlDrawer.vue`, скомпилированных в памяти и отрендеренных через SSR на Vue 3.5.40 рядом с двумя нативными вызовами `useId()`. Получены ID `v-0, v-1, v-0, v-1`; при `app.config.idPrefix="brand"` — `brand-0, brand-1, brand-0, brand-1`. Гидрация этого нового смешанного случая и ручная проверка скринридером не запускались.

**Исправление.** Префиксовать заголовки локально в `WlDialog` и `WlDrawer`, например `wl-dialog-title-${useWlId()}` и `wl-drawer-title-${useWlId()}`, сохранив согласованные `id` / `aria-labelledby`. Общий `useWlId` публично экспортирован из `composables`, поэтому его формат не менять в рамках этой правки. Замены только fallback `"v"` на `"wl"` всё равно недостаточно при заданном `app.config.idPrefix`. Регрессия — реальные соседние вызовы нативного `useId()`, с `idPrefix` и без него; сохранить SSR/hydration детерминизм.

## 4. Архитектура

### Сильные стороны
- Чёткие границы: компонент отвечает за DOM и контракт, поведение живёт в `utils/options`, `anchoredOverlay`, `overlayLifecycle`, `overlayStack`, `rovingFocus`.
- Vue — единственный peer, runtime-зависимостей нет.
- Токены из одного `source.json`, слои `wl.reset` / `wl.tokens` / `wl.components`, пять тем без форка компонентов.
- Конфигурация и сервисы привязаны к Vue-приложению; компоненты работают и без `WlConfig`.
- Быстрый путь в `useWlPt`: без пользовательского `pt` возвращается замороженный объект дефолтов.
- Позиционирование оверлеев собственное и аккуратное: переворот на противоположную сторону, ограничение по окну, учёт z-index якоря.

### Риски и долг
1. **Типы опираются на `__ctx`** — внутреннее поле результата vue-tsc (`generic-contracts.ts`, `choice-group-contracts.ts`, `native-contracts.ts`). Риск задокументирован в `docs/maintainers/architecture.md` и прикрыт типовыми тестами, но остаётся: обновление компилятора может ослабить вывод типов без ошибок сборки.
2. **`Teleport to="body"` зашит в 13 файлах.** Цель нельзя настроить. Это мешает Shadow DOM, микрофронтендам, элементам в fullscreen и приложениям со своим контейнером оверлеев.
3. **Вес обвязки.** Корневые скрипты — около 9,2 тыс. строк при 18,2 тыс. строк рукописного кода библиотеки. Каждая проверка полезна, но всё это нужно поддерживать одному человеку.
4. **Базовый снапшот совместимости — всё ещё 0.11.1.** Снапшот 1.0.0 значится в ROADMAP как невыполненный пункт. Пока его нет, обещание «патчи не ломают контракт» сверяется с дорелизной базой и набором исключений. *Обновление 14.11: закрыто в 1.1.0 — снапшот 1.0.0 заморожен и используется как база.*
5. **Замороженные имена.** Префикс `Wl` / `--wl-` при бренде Gavia, id тем `white` и `graphite` для Classic и Classic Dark. Решение принято в RFC, менять уже дорого; достаточно одного абзаца-объяснения в README.
6. **`MutationObserver` на всё поддерево `body`** при открытом модальном окне (`overlayStack.ts`). На каждую пачку мутаций заново обходятся дети `body`. Для диалога с активно меняющимся содержимым стоит замерить.
