# Release procedure

Release history is in [GitHub Releases](https://github.com/whitewolf06/gavia-ui/releases)
and the preserved [release evidence ledger](release-history.md). Historical
counts, hashes and deployment statements are not current verification.

For 1.0 preparation, use the [RC checklist](release-candidate.md),
[manual accessibility protocol](manual-accessibility.md) and
[unsent communication drafts](release-announcements.md).

## Prepare source

1. Obtain explicit authorization for release preparation and heavy checks.
2. Review changesets (`pnpm changeset:status`) and the root Unreleased section.
3. Apply the approved version plan with `pnpm release:version`. It synchronizes
   root/package versions and prepares the canonical root changelog; it does not
   publish. Complete the generated migration guide and remove TODO placeholders.
4. Review compatibility and required upgrade steps. Root LICENSE/changelog are
   canonical; package LICENSE, changelog and compact README are generated by
   `prepack` during `pnpm run pack`.

For a new prerelease cycle, use `pnpm changeset pre enter rc` on the agreed branch
before preparing versions. The current **1.0.0-rc.1** is already prepared in RC
mode; do not re-enter it or run version preparation merely to build/pack it.
Alpha/beta/rc.N archives use npm `next`; stable releases use
`latest`. Exit prerelease mode with `pnpm changeset pre exit` and prepare/check
the stable version separately. Do not use `changeset publish`.

The owner-approved [1.0 RC transition](../rfc/0001-public-api-1.0.md#accepted-rc-transition--2026-10-22)
replaces the originally planned separate 0.x warning release. Keep the feedback
window open for two to four weeks after confirmed RC publication; record its
actual dates before stable acceptance. No new local runs or delivery actions were
authorized by the 2026-10-22 source-preparation instruction.

## Verify and authorize delivery

Run the complete [release checklist](../../AGENTS.md#6-release-checklist--only-on-explicit-request)
and [quality checks](quality.md), including the installed archive, minimum/current
Vue consumers, declaration resolution, browser behavior, Windows screenshots and
Pages subpath smoke where applicable. Inspect screenshot diffs before updates.
Record NVDA/VoiceOver and owner acceptance separately. Do not lower thresholds
or replace compatibility fixtures to clear a gate.

Review source and validation first; commit, push, tag, npm publication and public
announcements each require the applicable separate authorization. A new
`vVERSION` tag starts `.github/workflows/publish.yml` (title **Release**).
It reuses the complete CI workflow, validates the exact archive in a browser
consumer and publishes that checked archive using scoped OIDC. Keep the
`publish.yml` trusted-publisher filename. The historical `v0.7.0` tag is excluded.
Repository/registry publisher settings are owner-managed.

## Read back publication

Verify npm version, channel and archive integrity after publication. A successful
build or tag is not proof that the registry serves the checked package. Update
published-version metadata only after that read-back; retain source-version
labels for prepared work.

The release workflow builds a portable Playground archive with a relative base,
records SHA256/provenance and attaches it to the GitHub Release. It also prepares
a verified TTF font ZIP with font notices. Those attachments do not deploy Pages.
Local preparation uses `pnpm release:preview` and
`node scripts/archive-fonts.mjs --output <explicit-path.zip>` only when authorized.

Pages has its own [same-revision deployment policy](ci.md#pages-provenance).
Confirm the public URL separately. npm notes link to immutable tag documentation;
the packaged changelog links to current main documentation.
